\section{Data and Measurement}
\label{sec:data}

\subsection{GitHub users and country assignment}
\label{sec:users}

The analysis begins from GitHub accounts returned by country-location searches for Bangladesh and fourteen potential donor countries: the Philippines, Pakistan, Sri Lanka, Nepal, Indonesia, Vietnam, Malaysia, Thailand, Kenya, Nigeria, Ghana, Morocco, Jordan, and Tunisia. GitHub profile location is self-reported. I therefore interpret the sample as accounts associated with each country rather than verified physical residence at every point in time.

For each account, I use GH Archive to recover public daily GitHub events from May 1 through September 4, 2024. I retain accounts with at least four pre-treatment active days and remove likely bots or automation accounts using login/name patterns and behavioral filters. The final eligible sample contains 59,158 users, including 10,241 accounts associated with Bangladesh. This restriction focuses the design on developers with observable pre-shutdown activity and reduces the influence of dormant accounts. It also means that the estimand is an effect on pre-active public GitHub users, not on every person who has a GitHub account.

\subsection{Outcomes}
\label{sec:outcomes}

The primary outcome is the daily active-user rate: the share of eligible users in a country who record at least one productive GitHub action on day $t$. This extensive-margin measure is preferred because GitHub activity is sparse at the user-day level and raw commit counts contain extreme outliers. Binary activity measures are also closely aligned with the approach used by \citet{kreitmeir2024}.

I construct secondary outcomes along the software-production pipeline. Productive activity indicates a day with commits, issue closure, pull-request closure, or a release. Shipping activity indicates a day with a merged pull request or a release. Collaboration activity indicates a day with code review or comment activity. I also construct count outcomes per 1,000 eligible users: collaboration events and shipping output. These measures separate code production from downstream delivery and coordination.

Count outcomes are winsorized in user-level regressions when appropriate, because a small number of accounts generate implausibly large daily or weekly commit counts. The primary country-day synthetic-control analysis does not rely on a raw commit-count headline. National holidays are coded at the country-day level and used in robustness checks.

\subsection{Commit-level mechanism data}
\label{sec:mechanism_data}

To distinguish coding from publication, I build a separate commit-level dataset for Bangladesh. I extract public PushEvents by eligible Bangladeshi users, retain PushEvents for which the historical payload reveals the complete set of commit SHAs, and keep the earliest observed push for each repository-SHA pair. I then query GitHub commit metadata to recover \texttt{authoredDate}, \texttt{committedDate}, and GitHub-linked author and committer logins. The analysis target contains 86,065 repository-SHA pairs; 70,576 commit objects are successfully resolved, an 82.0 percent resolution rate.

The strict mechanism sample requires (i) a non-missing author timestamp, (ii) a nonnegative author-to-push delay, and (iii) equality between the GitHub login linked to the commit author and the PushEvent actor. This leaves 59,920 commits. The equality condition avoids attributing a commit written by another person to the Bangladeshi user who happened to push it. Git author and committer timestamps are embedded metadata rather than independently verified work-time measurements, so they are interpreted as evidence consistent with offline production rather than as an infallible clock of when coding occurred.

\subsection{Sector-recovery sample and repository classification}
\label{sec:sector_data}

To study the period after connectivity returned, I construct a separate within-Bangladesh panel. It starts from the 23,866 Bangladesh-associated accounts with at least one day of selected public GitHub activity between January 18 and July 17, 2024, and draws a fixed sample of 20,000 of them. Eligibility depends only on pre-shutdown activity, so the sample composition cannot respond to the shutdown or to post-shutdown behavior. For these accounts, I recover all public GH Archive events from January 18 through November 23, 2024, aggregated to the user-repository-day level.

This sample differs from the 59,158-account synthetic-control sample in its eligibility rule (one rather than four pre-treatment active days), its observation window, and its restriction to Bangladesh, so its activity levels are not directly comparable with the country-day rates in \cref{sec:results}.

Each repository is assigned to a two-digit sector of the North American Industry Classification System (NAICS) by a publicly released multilingual transformer classifier that predicts a NAICS sector from repository text (\texttt{aquiro1994/naics-github-classifier-multilingual}) [CITATION NEEDED]. The classifier input is the repository name and a historical snapshot of the root README file. For repositories observed on or before July 17, 2024, the snapshot is taken as of July 17; for repositories first observed after the shutdown, it is taken as of their first observed activity date. Current repository descriptions and topics are deliberately excluded, because they may have been written after the study period. Of the 168,875 distinct repositories in the panel, a historical README is recovered for 92,979 (55.1 percent); the remainder lack a root README at the target date or could not be retrieved. The main specification assigns a sector only when the classifier's confidence score is at least 0.80, which holds for 32,491 repositories across all sectors; repositories below this threshold do not contribute to any sector. Thresholds of 0.70 and 0.90 are used as robustness checks.

The sector measures the economic sector associated with the repositories in which observable GitHub activity occurs. It is not the developer's employer or industry of employment: the same developer may contribute to repositories classified in several sectors, and a repository's sector describes the application domain inferred from its text rather than the organization that funds the work.
